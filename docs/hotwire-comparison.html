docs — Hotwire 対比ノート

Hotwire を使わずともよい、を体感する

ReActionView 0.6.0 + herb 0.11.1 の検証リポジトリ（Kaigi on Rails 2026 の主題検証）。 このページは静的HTML — ビルドもJSもなしで開けます。 本リポジトリの主張「ERB のみで Phoenix LiveView 的な細粒度リアクティビティ」を、 Hotwire（Turbo + Stimulus）が担っていた役割ごとに分解して、実コードで対比します。

目次: ① 主張の分解 ② 証明マップ（4画面） ③ 実コード対比 ④ 概念読替表 ⑤ 往復はいつ飛ぶか ⑥ 正直な境界 ⑦ 次に足すなら

①主張の分解 — Hotwire の2層を、モード2つで置き換える

「Hotwire 不要」を1文で言うと曖昧になるので、役割で2層に分解します。 ReActionView は各層を別々のモード（server / client）で置き換えます。モードはテンプレート冒頭のコメント1行で指定します。

Hotwire 層1  → ReActionView server mode

Turbo Frame / Turbo Stream / form の往復

DB を引く更新（検索・ソート・ページネーション・作成）。Turbo だと form + turbo-frame + 部分テンプレート＋枠外の値（合計バッジ等）を更新する Stream まで必要になりがち。 ReActionView は herb_state と data-herb-* 属性だけで、 同じアクションが HTML を出しつつ部分更新のワイヤも返す。

実装: /（Sprint Hub）と /patterns（Patterns）

Hotwire 層2  → ReActionView client mode

Stimulus コントローラ（リアクティブUI）

DB を引かない更新（文字数・妥当性・開閉・カウンタ・ステップ）。Hotwire だと Stimulus コントローラを書くこと自体が 「Turbo 外の生 JS 層」になった。client mode ではテンプレートが状態と分岐をコンパイル解析し、 クライアントへの命令書（manifest）を自動生成 — 操作は全てブラウザ内で完結（0 往復）。

実装: /lab（Client Lab）と /ui（UI Kit）

JS の実体（実ファイル・全4行）

// app/javascript/application.js
// Why not "controllers": the showcase is a zero-custom-JS demo — Stimulus
// wiring would only muddy the measured claim that ERB alone carries the UI.
import "reactionview"

importmap も同様

import "reactionview" の1-line で済み、node_modules もビルドも不要。 turbo/stimulus の pin は Rails 生成の標準配置（app/javascript/controllers/）には 1ファイルも無く、このアプリは import していない（無意味に残存するだけ）。 UI に必要なのは gem が自動 pin する reactionview クライアント 1本。

なお本リポジトリの制約「Node/yarn を導入しない → importmap で完結」は、この訴求と同じ土台にある。

③実コード対比 — 4つの局面

右は本リポジトリの実物（ファイル・行を切り出し）。左は Hotwire で同じ挙動のために 典型的に書かされるコード（代表的形の仮置き、本リポジトリには無い）。 「局所更新の配管」と「生 JS の部分」がどう消えるかを並べて読めます。

対比 1 — 検索の絞り込み（打たれるたびに活きる、DB引きの1往復）

Hotwire（Turbo Frame + Stimulus）3ファイル
// app/javascript/controllers/search_controller.js
import { Controller } from "@hotwired/stimulus"

export default class extends Controller {
  // Turboには「input単位の submit」が無いので自作する
  submit({ target }) {
    clearTimeout(this.timer)
    this.timer = setTimeout(() =>
      target.form.requestSubmit(), 220)
  }
}
<!-- app/views/tasks/index.html.erb -->
<%= form_with url: tasks_path, data: {
  turbo_frame: "tasks" } do %>
  <%= text_field_tag :query, params[:query],
    data: { controller: "search",
            action: "input->search#submit" } %>
<% end %>

<turbo-frame id="tasks"> … </turbo-frame>
置く場所が3つ: Stimulus コントローラ / form＋frame / 部分テンプレ。 さらに枠外のバッジ（全件数）は frame の外なので、Turbo Stream か frame 増設で別途配管が必要。
ReActionView（実物: app/views/tasks/index.html.erb）属性1つ
<input class="field" value="<%= query %>"
  data-herb-set="query=$value"
  data-herb-debounce="220"
  placeholder="タスクを検索…">
<%# 反転する分岐が往復の「スイッチ」になる (機能①) %>
<% if query.empty? %>全件表示<% else %>
  「<%= query %>」の結果（サーバーで絞り込み済み）
<% end %>

<%# app/controllers/tasks_controller.rb — 同じアクションが応答する %>
term = herb_state("query", "")
@tasks = Task.order(created_at: direction)
             .where(...) if term.present?
オプション1行＋「if query.empty? の反転」が往復のトリガ。 行もバッジも同じ往復の slots ワイヤで一体に更新されるので、部分更新の配管を複数作らない。 文字入力中は分岐が反転しない限り通信なし — debounce は属性備え付け。

対比 2 — 楽観的追加（押した瞬間に行が入る）

Hotwire（Stimulus 楽観挿入 + Turbo Stream 正）2ファイル
// 楽観的に置くには Stimulus で先に DOM を作る —
// 差し込み口・順序・キーの整合は自前管理になる
export default class extends Controller {
  static targets = ["list", "row"]
  submit(event) {
    event.preventDefault()
    const li = this.rowTarget.content
      .firstElementChild.cloneNode(true)
    li.querySelector("[data-title]").textContent =
      event.target.querySelector("[name='task[title]']").value
    this.listTarget.prepend(li)
  }
}
<!-- 後から「正」が届く配管は別 — 例: Turbo Stream -->
<!-- app/views/tasks/create.turbo_stream.erb -->
<%= turbo_stream.prepend "tasks", @task %>
楽観側と正側が別の仕組みに別れがち。順序や重複、キー照合は手で管理する領分。 （もっと手軽に Turbo Frame で送るなら、それは往復待ちの描画になり楽観でなくなる）
ReActionView（実物: app/views/tasks/index.html.erb）属性3つ
<form action="<%= tasks_path %>" method="post"
  data-herb-into="tasks"
  data-herb-set="submit->drawer_open=false"
  data-herb-reset="submit->title">
<%# app/controllers/tasks_controller.rb — 201で新規「行」だけ届ける %>
format.slots do
  @tasks = Task.where(id: task.id)
  render :index, status: :created  # 201 + 行のstatics
end

<%# no-JS の従来フォールバックも同じコントローラで %>
format.html do redirect_to root_path, notice: … end
201 応答の collection splice。クライアントはキー付き照合で新規行だけ差し込み（既存行は動かない）、 その行の statics は GET と同じテンプレーコンパイルから出るので整合が取れている。 ドロワーを閉じる/クリアする data-herb-set/-reset も form と同時発火。

対比 3 — ライブ入力とバリデーション（ここが Stimulus の独壇場だったはず）

Hotwire（Stimulus）2ファイル
// app/javascript/controllers/char_count_controller.js
export default class extends Controller {
  static targets = ["input", "count", "submit"]
  connect() { this.update() }
  update() {
    const v = this.inputTarget.value
    this.countTarget.textContent = `${v.length} 文字`
    this.countTarget.classList.toggle("over", v.length > 60)
    this.submitTarget.disabled =
      v.length === 0 || v.length > 60
  }
}
<textarea data-controller="char-count"
  data-action="input->char-count#update">…</textarea>
<span data-char-count-target="count"></span>
<button data-char-count-target="submit">保存</button>
文字数・上限判定・disabled を手で同期。 Turbo に入力毎の反応機構は基本無いので、これはどの実装でも Stimulus に落ちる。 （Turbo Stream 往復で作るなら打鍵ごとの点滅になる）
ReActionView（実物: app/views/showcase/lab.html.erb）宣言1行
<%# herb:state (draft: "",
  ready: draft != "",
  bio: "",
  ready_bio: bio != "" && bio.length <= 60,
  over: bio.length > 60) %>

<textarea value="<%= draft %>"></textarea>
<p><%= draft.length %> 文字
  <% if ready %>・送信準備OK<% end %></p>
<button disabled="<%= !ready_bio %>">保存</button>
派生状態の宣言（ready_bio: bio != "" && bio.length <= 60 は コンボ派生、over は length 変換＋順序比較として manifest に入る）だけで、 文字数・出し分け・disabled 全部が 0 往復で反応する。書くのは「読み」だけ。なお textarea は value= 対応なので送信後のリセットも表示まで追従する。

対比 4 — 行ごとの数量ステッパー（per-item 状態）

Hotwire（Stimulus）1ファイル
// app/javascript/controllers/stepper_controller.js
export default class extends Controller {
  step({ currentTarget, params }) {
    const row = currentTarget.closest("[data-row]")
    const qty = Math.max(0,
      (Number(row.dataset.qty) || 0) + params.delta)
    row.dataset.qty = qty
    row.querySelector(".qty").textContent = qty
    row.querySelector(".minus").disabled = qty === 0
    this.recalcTotal()  // 全行走査して合計を張り直す
  }
}
行ごとの状態は JS 側の dataset に置く（HTML から見えない）。 合計の再計算も Stimulus 預け（逆にここなら金額×数量も書ける — 後述の境界と引き換え）。
ReActionView（実物: app/views/components/ui/_stepper.html.erb）属性1組
<%# herb:state (in_cart: 0) %>   <%# 行ごとに: %>
<%# herb:state (qty: 0) %>

<button data-herb-decrement="qty"
  disabled="<%= qty == 0 %>">−</button>
<span class="qty-value"><%= qty %></span>
<button data-herb-increment="qty">＋</button>
<% if qty > 0 %><% in_cart += 1 %><% end %>

<%# 統計はリストの直後（foldが完了してから読む） %>
<%= in_cart %> 点をカートに追加
state は HTML に住んでいる（行ごと宣言、hidden への presence）。キー付き item に紐づいた状態なので 行が増減しても state が行に追従する。なお in_cart はカウントfold（+= 1 の整数リテラル増分 のみ）— 金額合計は「クライアントでは作れない」が正確な境界（§6）。

⑤往復はいつ飛ぶか — DevTools で数えられる形で

「Turbo より通信が減る」は口でなく ?format=slots のリクエスト数として読めます。

server mode（/, /patterns）

往復はstate を読む分岐の答えが反転した時だけ1回。 検索の分岐反転は <% if query.empty? %> がトリガ、ソート select 単体は 0（実測）。 連続タイピングで分岐が反転しない間は行を触らず、文字はクライアント評価で更新。

なお steering（Herb-State ヘッダ）に載るのは 分岐の条件が読んでいる state に限る。 往復させたい state は必ずどこかの state 条件分岐に読ませる — Patterns の3本柱（if / elsif 連鎖 / page > 1 / selected_id > 0）はその実装。

client mode（/lab, /ui)

全操作 0 往復。未描画ブランチは初期レスポンスの <template data-herb-region> に格納済みで、 <template data-herb-manifests>（states/reads/conditionals/presence/computed の命令書）に従って ブラウザ内で分岐の materialize・presence・fold が進む。

UI Kit の9コンポーネント全操作は slot 往復 0 を実測（docs/ui-kit.md）。意図的に同期取り直したい時だけ data-herb-action="$refresh" が脱出ハッチ。

共通の帳尻

  • $refresh 等の action は data-herb-set と同要素に併置できる（同 dispatch の state は 1 リクエストに合流）
  • no-JS 環境では form が通常の POST → format.html の redirect／flash で完結（フォールバックの振る舞いを統合テストで固定）
  • 応答は HTML でなく値の JSON（application/vnd.herb.slots+json）— 行まるごとの再送ではない

⑥正直な境界 — 0.6.0 時点の実測で書けないもの

営業コピーではなく実測ノートなので、クライアント評価が届かない枠も並べます。どれも対処パターンが確立済み。

  • 演算・金額合計は fold に載らない — fold の増分は整数リテラルのみ（<% in_cart += 1 %> の3タグ形）。 total += price * qty 系は設計段階で諦め、サーバー側の READ slot（1 往復）に置く。 派生の変換テーブルも .length / .size / .to_s のみ。
  • ループデータとの比較は literal のみ — task.id == selected_id は ErrorInTemplate。 コントローラから ivar（@selected_id）を渡し、per-row の属性スロットとして往復させる（patterns の実装）。
  • per-item 分岐に置いたサーバー読みの値は空で届く — statics は materialize されるが値は乗らない（0.6.0 実測）。 対処は「答えを分岐の中に置かない」：hidden="<%= !open %>" の presence バインディング＋CSS[hidden]ガード （lab 機能⑭、ui コンポーネント全体）。
  • パーシャル内の分岐先は parked されない — client mode でも region テンプレート自体が出ない（ui-kit 実測）。 パーシャルでは分岐でなく presence（hidden）＋CSS で切替、が定石。
  • POST 201 の splice は collection のみ — region 級のサーバー読み（Task.count 等）は次の GET でしか追いつかない。 追加直後の hero は $refresh 頼み、という手順を見せるのが誠実。
  • server モードでブラウザ所有 state を条件にした分岐を置かない — steering に載らず、要求が常に行禁化（要求 storm）。 見た目は presence＋CSS、数値は READ slot へ。

この境界の読み方: 「Stimulus を捨てると何ができなくなるか」が暗黙でなく明文化されているのが 検証リポジトリとしての価値。bin/rails test は HTMLレンダ / herb_state による並び替え / slots 応答 / no-JS フォールバックの振る舞いを固定しているので、境界の再現性もコミットで追跡できます。

⑦次に足すなら — 「Hotwire 不要」をさらに刺す候補UI

既存4画面で足りないのは「まだ Hotwire で書かざるを得なかった箇所」を捨てた新局面。3候補。

最有力 行とヘッダの同時連動（ピン/星）

行の星を押すと、行の見た目とヘッダの「ピン済み N」が即時に揃う。 星の塗りは presence バインディング＋CSS、N はカウントfold（when: "pinned"）でクライアント評価 — 0 往復。Hotwire なら2か所の DOM 同期（Stimulus）か Stream 往復が要る。

既存の実測パターン（presence + fold + toggle）の組合せのみで組める。

横並べ比較画面（/compare）

turbo-rails を Gemfile に足し（importmap pin のみ・ビルドレス）、同じタスク管理を Turbo Frame/Stream 版と ReActionView 版で並べ、Network 往復とコード量を横に対応させる。 決定的な説得力はあるが、Gemfile 変更の範囲確認が必要。

本ページの§③の対比を実物として隣に置く形。

送信前計算フォーム（送料・合計）

入力に連動して合計や保存ボタンが変わるUI。price * qty は fold 外なので READ slot の 1 往復で答える「正直版」— Hotwire では Stimulus なしに書けない局面を ReActionView が1往復で置く形を示せる。
